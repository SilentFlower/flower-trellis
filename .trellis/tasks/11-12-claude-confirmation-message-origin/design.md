# 技术设计

从当前 Claude Hook 的 runId、promptId 和回合状态定位当前回合，用结构化来源核对该回合。只在有界窗口内查找精确的当前 promptId，定位过程无需判断更早记录的来源或正文；当前证据未写完或无法定位时保持人工。当前回合是有效内部唤醒时，保持既有连续确认路径，按原生通知与所属请求的匹配关系核实回合归属。

以当前回合对应完整记录的边界开始观察，避免取最新 EOF 时漏掉已经追加的新输入。冻结文件身份和边界，独立的 wait、claim、started 进程从同一观察起点续读。准备阶段复查 Hook 代次与边界之后的记录，覆盖 Hook 与 transcript 的写入竞态。继续使用原有文件替换、截断、runId 和单次领取约束。参考 `src/assets/flower_confirmation_runtime/claude.py:110`、`:209` 和 `src/assets/flower_confirmation_runtime/runtime.py:147`、`:219`。

观察起点之后，核对真实人工输入的结构化来源并作废旧等待。明确的 `peer` 和仅落日志通知跳过。唤醒证据必须来自观察范围内，继续与 Hook 对应的后台任务、本次请求和当前回合交叉核对。Hook 的通知正文识别只产生候选；人工粘贴相同文字仍由结构化来源判为人工。

本任务和容量、Windows 任务触及同一适配器与日志读取。基于现有增量日志逻辑做局部调整，本轮交付限 `flower-trellis` 源码和本仓投影。

Codex 从原生输入 Hook 的 `turnId` 定位 rollout 的回合开始事件，复用有界尾部定位、文件身份和续读边界。单独读取首条 `session_meta` 校验线程身份。从该回合查找最近的原生 `UserMessage`，以完整输入记录后的边界冻结基线。同一回合在准备前的插话纳入基线；准备后续读检测新输入、回滚、回合切换及队列唤醒。真实连续唤醒须匹配之前已领取的请求。Linux/WSL 与原生 Windows 共用读取契约，仍各用现有前台身份核验；分开记录实机与替身证据。
