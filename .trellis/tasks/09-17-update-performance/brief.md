# Brief — 升级链路性能诊断与优化

## Goal

- 缩短新版本升级和 `ftl update` 的可避免等待，并能看清每个阶段的耗时。

## Scope

- 复用有效版本缓存，轻量查询版本，按需加载发布说明。
- 消除 Flower 更新中的重复上游版本查询，优化全局 Trellis 版本探测。
- 增加可选的本地阶段计时，检查共用逻辑的 init/self-check，建立性能回归基线。

## Non-Goals

- 本轮不发布或执行当前项目的真实升级，不改代理、依赖选择或遥测采集；保留备份、安全校验和失败恢复。

## Key Decisions

- 手动强制刷新继续有效；版本与摘要请求共用原有 5 秒预算。
- 仅在 Flower 管理的更新中跳过 Trellis 独立版本提示查询，保留本地版本校验和其它网络功能。
- 全局版本快路径必须有真实安装证据，否则回退原探测；计时默认关闭，开启后只输出本地诊断。

## Key Context

- 主要涉及 update/self-update 编排、update-check/self-check、trellis-runner 和 global-trellis-sync。
- Linux 隔离实验中，跳过上游查询使更新预演中位数从 1.36 秒降至 0.46 秒；这是规划期局部实验；产品优化已实现，最终完整预演五轮中位数为 2.144 秒 → 1.524 秒。

## Risks / Deferred

- 用户环境中的下载、解包、原生模块编译耗时尚未确认，需阶段诊断；本轮暂不重构插件事务和文件遍历。
- 上游引导与全局命令识别须验证 Windows/Ubuntu，不能以本地 Linux 结果替代。

## Acceptance

- 有效缓存无必要补拉时零联网；Flower 更新不再发送上游独立版本查询；标准全局安装避免启动 CLI 取版本。
- 至少五轮前后对照；新版提示、发布说明、重复更新、预演、配置保留和失败恢复均通过回归。
- 帮助、JSON、退出码兼容；本地测试通过，最终提交的原生 Windows/Ubuntu 必需 CI 成功后完成验收。

## Next Step

- 首轮业务已推送；Windows CI 暴露非交互退出与测试权限假设问题，已完成本地补修，待补充提交确认及新 SHA 原生 CI 验收。
