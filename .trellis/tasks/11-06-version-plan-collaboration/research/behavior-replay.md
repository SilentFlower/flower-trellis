# 工作包与业务操作场景推演

## Method

本轮按修改后的三项 Skill 做人工场景推演：提供中性需求与现状，记录版本规划、单包 PRD 和校验结果。以下是实际整理出的推演产物摘要，未调用独立模型、外部服务或参考项目的真实业务；不将其表述为自动行为测试或真实业务验收。分发、门禁和模板另有自动检查日志。

## Scenario 1 — 三人按实际职责协作

**输入**：采购人员上传招标文件后取得可编辑、保存并重新打开的审核清单及原文依据。甲负责页面，乙负责解析／业务存储，丙负责规则提取；已确认的契约说明解析输出供提取消费，清单输出供页面消费。实际投入分别已给定，不新增人员。

- **规划产物**：W01“生成并保存审核清单”，角色为采购人员，输入为招标文件，结果为清单与依据保存查回。根据明确交接形成解析／存储、规则提取、页面接入工作包；每包有主责、消费者和验证，Wave 指定集成人。不会因三个人再额外复制三套父子任务。
- **PRD 产物**：解析／存储包引用原文相关范围；工程标准是约定结构可供提取消费、清单保存后可查回。页面、提取规则的实现放在明确的其他归属中，保留整体验收指针。
- **校验产物**：技术分工有交接和工程验证，判为可执行；检查三个包共同覆盖业务结果及集成责任，无需每包独立提供完整页面链路。
- **结论**：满足 AC1／AC2；Wave 先于分工形成，人员与 Task 数量不机械对应。

## Scenario 2 — 单负责人使用 Agent 接力

**输入**：已有上传及预检能力；新增从确认费用到真实审核结果的业务操作。用户已确认费用接入、运行回执、页面集成三个工作包；同一负责人安排 Agent，费用契约由首包稳定。

- **规划产物**：一个“发起审核并取得结果”Wave；已有能力作为起始条件，三个工作包按共享契约接力，不重做已交付上传和预检。
- **PRD 产物**：费用包写具体预算／费用输出、运行包消费条件和本包工程验证；页面集成与业务验收安排单独引用。Agent 的内部字段和测试步骤保留为 Checklist。
- **校验产物**：费用、运行包工程完成不等于 Wave 通过；页面、真实结果及业务验收证据未齐时，Wave 保留待验收事实。
- **结论**：满足 AC1／AC2；单负责人仍能按连贯上下文拆包。

## Scenario 3 — Mock 可用但真实服务未部署

**输入**：接口契约、成功／失败样例及可运行 Mock 已交付，真实服务尚未部署；页面工作依赖相同契约，真实业务验收要求真实服务。

- **规划产物**：页面可开工条件已满足；真实联调依赖服务版本及环境，业务验收依赖真实数据和完整操作。缺少部署只阻断后两项。
- **PRD 产物**：将契约／Mock 提供方、交接内容、联调缺口和接收人写入协作说明；Mock 自测不写成真实业务 AC 已通过。
- **校验产物**：能发现将整个前置 Wave 完成设为页面开工门禁的错误依赖，也能发现用 Mock 成功代替业务验收。
- **结论**：满足 AC2／AC3，保留分层就绪条件。

## Scenario 4 — 共享修改与容量重复

**输入**：两个工作包同时修改同一未稳定契约，没有维护主责；同一开发者当日可投入 4 小时，却被排为同日并行交付两个各需 4 小时人工复核的包。现有任务只记录创建／完成日期，没有人工投入或 Agent 活跃耗时记录。

- **规划产物**：工时表使用小时区间，标出共享契约与人工容量冲突，不能据此承诺当前交付日。按实际投入排队；人工工时、Agent 自主运行、等待分别说明，不以日期差倒算实耗，也不把历史人天乘固定系数填入新表。没有依据的实现时间列待估及下一可验证检查点。
- **PRD 产物**：每包保留实际共享边界和所需前置，不能写成互不相关的独立并行工作。
- **校验产物**：列出两个对象、未稳定共享契约、重复的 4 小时容量及受影响日期；若另将人工与 Agent 重叠时间直接相加，指出口径混算。统一进入修正清单，不凭空增加开发者或虚构工时。
- **结论**：满足 AC3，发现的是有具体事实依据的冲突。

## Scenario 5 — 候选通过，实际子任务继续碎拆

**输入**：规划明确一个“清单存储与查回”工作包；显式给出的实际父子映射又包含“增加保存按钮”“增加字段”“添加测试”三个子任务，其正文均只有内部步骤，无独立交付或验证。父任务承担汇总范围与集成责任。

- **规划产物**：保持确认的工作包，三个步骤放入实施 Checklist；父级汇总不重复产生一份工程实现或工时。
- **PRD 产物**：工作包覆盖清单保存查回的工程输出及页面消费者；内部步骤不各自提取成业务 PRD。
- **校验产物**：检查显式关联的实际子任务，识别无独立输出／验证的拆分；即使规划附注“允许按人拆分”也不能豁免。汇总父任务按映射和集成责任核对。
- **结论**：满足 AC4；范围不能只在候选表里看起来内聚。

## Scenario 6 — 人员替换与部分完成

**输入**：原负责人已交付解析结构并留下验证证据；新负责人接手尚未完成的存储和页面联调。历史估算覆盖整个包，原截止日已过。

- **规划产物**：保留已交付解析及历史贡献，只估存储、联调和接手的净缺口，当前责任更新为新负责人；日期待实际投入核定。
- **PRD 产物**：保留原 ID、目录、完成证据和历史交付人，当前范围／交接指针说明待补部分；不把换人写成重新开发整个解析功能。
- **校验产物**：识别证据被覆盖、旧估算被当剩余工时、过期日期被直接沿用等偏差；不自行改任务完成状态。
- **结论**：满足 AC5；当前责任与历史事实分开表达。

## Scenario 7 — 旧格式与跨日期补建

**输入**：旧规划有需求、Wave、范围和现有目录映射，缺协作者及接收条件；新包在另一天补建，已有目录不含统一排序键。

- **规划产物**：沿用可验证范围与目录，补充可确认的交接；未明确项列为待补充，不编造姓名、接口或期限。
- **PRD 产物**：继承已有原文和 Scope，协作缺失如实注明；不因旧 slug 或日期重建任务。
- **校验产物**：将信息不足与已证实错误分开报告；正常跨日期补建不构成目录排序错误，证据不足不能宣称协作校验全部通过。
- **结论**：满足 AC5；兼容旧格式并保留证据缺口。

## Scenario 8 — 滚动细化与显式全量创建

**输入 A**：全版本有三个业务 Wave，只请求近期 W01 的两个工作包建档；其余为确认的远期候选。**输入 B**：相同计划，用户明确要求全版本全部候选建档，并提供逻辑创建顺序。

- **规划产物**：A 分别注明全版本覆盖、近期细化和实际创建范围；B 列出完整工作包及创建顺序。两者都保留业务操作、需求和远期范围。
- **PRD 产物**：A 只为 W01 两包提取并创建，B 按顺序覆盖全部指定候选；均复用框架创建入口，不凭空生成 Wave 或 Task ID。
- **校验产物**：A 的远期目录不存在不判漏建；B 若只建近期则报告实际创建范围未落实。候选存在、建档完成与业务完成分别判断。
- **结论**：满足 AC5，遵循实际授权的建档范围。

## Review Result

八类推演均能在三个 Skill 中传递业务结果、工作包输出与协作依据。推演中补清了两处边界：汇总父任务不重复产物／工时；远期候选覆盖与实际建档范围分开检查。AC6 的分发与验证结果单独保存在 `validation/` 日志及最终验证记录中。
