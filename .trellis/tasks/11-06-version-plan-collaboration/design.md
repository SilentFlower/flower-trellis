# 版本规划与协作信息设计

## Architecture

本轮只调整三个 Skill 的文案、产物结构与判断规则，不增加运行时。`plan-version` 产生规划，`extract-prd` 在确认边界内提取单个工作包，`verify-task` 核对来源、相关实际任务与集成关系。

| 层级 | 负责的结果 | 与协作的关系 |
| --- | --- | --- |
| 版本 | 全部需求与范围覆盖 | 团队总投入、交付顺序和未决项的总览 |
| Wave | 一组业务操作形成的可验收结果，作为提测／交付批次 | 明确角色、起始条件、操作、结果、集成责任和通过条件 |
| Task | 上下文连贯、可实施和验证的工作包 | 有主要责任人，可包含协作者或 Agent；说明输入、输出与消费方 |
| Checklist | 包内实施、自测、修复步骤 | 不因多人参与或步骤多自动创建独立 Task |

这里的 Task 工程完成仍遵循当前检查、提交和 Close 生命周期；不新增状态，也不弱化原验收标准。跨 Wave 共享能力说明首先服务的批次和后续消费方，不强制一个 Wave 对应一个父 Task。

## Wave And Business Operations

用户明确希望 Wave 与业务操作挂钩，因此规划顺序调整为：业务角色与目标 → 操作及其结果 → Wave 边界 → 已有能力与实现缺口 → Task 与人员分工 → 依赖、容量与交付顺序。

每个 Wave 用一句话表达：“谁，在什么业务前提下，完成哪些操作，得到什么可以验收的结果。”验收从真实业务操作出发，确认结果可查询、可继续使用，以及该范围内要求的失败处理；不以内部接口数或开发人数衡量完成。

以下仅为标书审核业务的粒度示例，不迁移参考项目既有 Wave：

| 示例 Wave | 业务操作 | 可以停下来验收的结果 |
| --- | --- | --- |
| 生成并确认审核清单 | 上传招标文件 → 解析和提取 → 查看／调整 → 保存 | 审核清单及原文依据可用，保存后可重新打开并供后续审核消费 |
| 发起审核并取得结果 | 准备轮次／单位／响应文件 → 预检 → 确认费用 → 开始审核 → 查看结果 | 一次真实审核完成，费用、状态、问题和证据可查 |
| 完成人工复核 | 筛选问题 → 查看原文证据 → 作出判断 → 保存 | 人工结论和修改记录持久化，后续输出可以读取 |
| 获取审核交付物 | 选择输出范围 → 生成报告／批注副本 → 下载 | 获得与选定范围、审核及复核结果一致的文件 |

一个操作能形成独立有用的结果时可以构成一个 Wave；多个紧密相连的操作共同形成结果时可以合并。具体数量根据实际业务与交付目标确定，不把上述示例变成固定模板。已有能力可直接作为起始条件，不要求每个 Wave 重做前面的完整业务流程。

格式扩展、图片检查或历史查询等范围，按其新增或改变的业务操作、可验收结果判断归入已有 Wave 还是另列 Wave。纯契约、公共组件或环境准备通过支撑 Task 关联业务 Wave，工程准备进度单独说明。业务流程顺序与开发排期分别表达，满足输入条件的工作可以并行。

## Collaboration Contract

信息优先写入现有版本规划和任务文档，不新建 JSON schema 或多份权威台账。

| 信息 | 版本规划落点 | 单 Task 落点 | 校验关注 |
| --- | --- | --- | --- |
| 责任与能力 | 拆分前的团队约束；候选负责人、协作者和 Wave 集成人 | 本任务交付与协作说明 | 责任遗漏、同一人容量重复、无法核实的人员映射 |
| 输入、输出、消费方 | 工作包描述及依赖关系 | 交接内容、契约／基线指针及接收条件 | 只有任务号却没有所需交付；接口语义冲突 |
| 代码边界 | 已核实的仓库／模块与共享改动归属 | Technical Notes；具体实施细节进入 design／implement | 重复建设、共享文件并行修改、未稳定契约 |
| 就绪条件 | 分别说明开工、联调与业务验收前提 | 本包实际依赖及阻断影响 | 把整个前置批次当成无条件串行门禁；循环依赖 |
| 完成证据 | 工作包工程结果与 Wave 业务结果分列 | 工程完成标准及对应的业务 AC 片段 | Mock、自测、合入、部署和业务验收混用 |

协作信息的细度随团队和依赖裁剪。单人、简单无依赖工作包可用几行说明；多人、跨仓库或共享契约工作包才展开相关表格。未知信息标注来源不足或待定，不填造假身份、日期和能力。

## Skill Changes

### Plan-Version

1. 保留全文需求扫描与原文追溯；把“唯一真相”限定为业务需求内容，不把工程现状和已确认人员决定混作需求原文。
2. 在候选拆分前读取角色、投入、已有能力和协作模式。候选阶段即说明工作包输出、责任与交接；后续估算据此检查负载和关键路径。
3. 修改拆／并判断：技术层和人员变化只是信号，是否形成稳定交接、独立工程验证以及可控改动边界才决定是否独立成 Task；包内步骤继续用 Checklist。
4. Wave 明确业务角色、起始条件、操作、可验收结果与集成验收负责关系。纯前置能力作为支撑工作包关联具体业务 Wave，工程准备不占用业务 Wave 的定义。
5. 扩展现有 `任务拆分与waves.md` 和 `开发计划-工时评估.md`；已有需求覆盖确认、拆分评审门禁继续由本 Skill 负责，不引入额外确认轮次。
6. 将逻辑创建顺序与开工条件区分；保留新建任务的稳定排序 slug 建议，不要求改名已有目录来模拟依赖或人员分组。
7. 保留 `开发计划-工时评估.md` 入口，工时默认按小时（h）区间表达。基于当前人＋Agent 方式估工作包实现、自测、联调和验收修复，注明作业耗时／人工投入的口径及依据；Agent 运行、人工参与和外部等待分开，不将旧人天乘固定系数当作重新估算。缺少实耗时先列缺口和检查点，不从任务日期差倒算开发工时。

### Extract-PRD

1. 从已确认版本规划继承交付与协作信息，保留原始需求原文、Requirements／AC 索引及来源标注。
2. 在现有 Scope 之后加入按需的“交付与协作”内容：负责人／协作者、输入输出／消费方、工程验证、集成归属与前提。未存在协作规划时不编造。
3. 工程完成标准以确认范围、实际契约和代码证据为依据，与原始业务 AC 片段分开表述；设计与具体命令仍留给 design／implement。
4. 复用 `assignee`、`relatedFiles`、`meta.version_plan`、`meta.wave`、`meta.source_requirements` 的现有能力；本轮不新增 metadata 协议。实名到开发者标识未核实时不猜测赋值。
5. 更新已有任务时保留原完成证据和历史归属；批量只创建用户指定的已确认范围。滚动规划允许远期只有候选，显式全量请求则完整创建。

### Verify-Task

1. 延续当前准确性、覆盖、UI 文案和跨层校验；版本规划部分按工程工作包与 Wave 业务验收分别判断。
2. 除候选外，读取由明确规划路径、映射和父子关系识别的实际相关任务；不凭目录姓名或标题猜关联，不扫描并改动无关任务。
3. 将输出、工程验证、消费／集成路径作为粒度判断依据；移除“规划允许即可通过”的豁免，也避免所有按层分工都被判碎拆。
4. 在既有统一报告和一次性修正清单中纳入责任缺失、容量重复、依赖缺交付、共享冲突、循环和集成验收缺口；不增加另一轮逐项审批。
5. 老产物信息不足报告待补充，正常滚动候选不判为漏建；目录自然排序不作为重命名历史任务的理由。真实边界或来源冲突继续按实质问题处理。

## Compatibility And Ownership

- 0.6 的 `.agents` 与 `.claude` 两套维护源同步更新；old／0.5 不变。
- 先修改 `vendor/skill-garden/.trellis/0.6/`，再 `npm run sync`；按需刷新 compiled targets 并运行漂移检查。
- 根项目 `.agents`／`.claude` 副本经 Flower 的现有 preflight 与事务更新，保留其他 Plugin 和用户修改；不手工更改 lock／state hash。
- 现有 Brief `Context & Decisions` 足以承接已写入 PRD／design／implement 的责任和前提，本轮只验证其派生结果；brainstorm、route 和 Check-All 不新增另一份协作协议。
- 过程主干留在 SKILL，详细场景或模板只有在影响可读性时按需下沉到所属 Skill 的 references；不添加无消费者的公共规范副本。

## Validation Scenarios

| 场景 | 应观察到的行为 |
| --- | --- |
| 三人分别承担页面、业务后端、工作流 | 先以“上传招标文件至清单保存查回”等业务操作和结果定义 Wave，再形成有交接的工作包／包内协作；层次本身不自动决定建 Task |
| 单负责人调度 Agent，费用→运行→页面接力 | 根据共享契约和验证边界拆包；每包可自证输出，最终真实业务验收单独收口 |
| 契约／Mock 就绪但真实服务未部署 | 消费者可先开发和自测，真实联调及 Wave 验收仍保留前提 |
| 两包修改同一未稳定 DTO，一个人承担两条关键路径 | 以小时区间说明口径、主责与接力，不重复计算人员容量或人工／Agent 重叠，不将缺少依据的日期差当实耗 |
| 候选合理，但实际子任务变成字段／按钮／测试碎片 | 校验实际任务并指出无独立输出／验证的拆分；不能仅凭规划许可通过 |
| 人员替换且旧任务已部分完成 | 当前责任更新，历史交付人及已完成证据保留，按净缺口重估 |
| 老规划无协作字段，跨日期新增任务 | 提示证据不足并保留现有标识，不编造分工或强制改名 |
| 滚动规划与显式全量创建分别调用 | 前者不自动建立远期目录；后者按确认顺序完整建立指定工作包 |

场景检查使用中性材料和隔离产物，不复跑参考项目的模型、服务或外部 Issue 操作。

## Tradeoffs And Rollback

三个 Skill 共同维护同一信息流，拆成独立任务会产生中间语义不一致，因此作为一个交付。新增字段限制在文档，降低运行时和旧项目迁移成本。验证发现规则使正常技术协作无法表达，或导致候选继续膨胀时，优先修正拆分准则，不增加更多层级。

回退本轮源文案和对应同步产物即可；不对参考项目或历史任务做迁移，因此没有业务数据回退步骤。
