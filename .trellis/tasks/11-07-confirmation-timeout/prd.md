# 跨 Harness 确认点超时默认决策

## Goal

为 Trellis 的日常确认环节提供可分别配置的超时默认决策，减少等待，同时保证人工决定优先、主会话退出即取消，并按 Harness 的实际能力提供兼容支持。

## Background

- 用户希望等待时长随需要阅读和判断的内容增加；时长以秒配置，提交行为沿用原流程。
- 用户明确关注主会话退出后是否还会恢复对话，并要求考虑 Codex 以外的 Harness。
- 当前日常确认主要涉及首次 Brief、Check-All 问题处置和提交推送计划。Spec 更新通常自主完成，仅无法从证据消解的歧义需要人工决定。
- 此前建议的固定 60 / 30 / 30 秒与 `queue --resume` 均不采用；后者可能恢复退出的会话，不能满足本任务的退出边界。
- 原生后台终端已先行实测，结果见 [研究记录](research/native-background-results.md)。用户随后接受 Codex 与 Claude 都通过统一前台入口接入标准等待工具，并授权隔离实验，避免依赖各平台不同的后台完成通知。

## Requirements

- R1：Brief 正文 1000 字以内等待 100 秒，超出部分每 500 字增加 30 秒，不足 500 字按一档计算；检查首个待处置问题等待 100 秒，每多一条增加 30 秒，无待处置问题时不产生等待；提交确认固定等待 200 秒。三类策略独立，支持按秒调整和关闭自动选择。
- R2：超时默认动作必须有明确适用授权。等待前完整展示当前方案、默认选项及超时安排；计时不从任务创建或方案生成开始。
- R3：自动选择尚未开始时，用户回复、暂停、取消或修改方案可以阻止旧默认选择；方案或范围变化后，旧确认失效。
- R4：功能只在当前主会话有效时生效。主会话退出后不再发起新的自动执行，不自行恢复会话；用户之后手动重新打开会话也不补跑旧待决事项。
- R5：自动动作已经开始后发生退出，按 Harness 的中断能力处理，已完成的副作用不伪装为已撤销。
- R6：首版实际支持 Codex 与 Claude Code，共用决策规则；两个平台都必须验证人工输入、超时继续及退出取消。其他 Harness 保持原有人工确认，并说明尚未开放自动模式。
- R7：同一事项不得因重复通知、并发输入、工具重试或会话恢复而重复执行；记录决定来源，区分人工选择和已授权的超时默认选择。
- R8：超时选择只决定进入哪个既有动作，继续遵守该动作所属流程的检查、文件范围、计划有效性和执行结果核验。
- R9：取消此前提出的“超时只做本地 commit”特殊规则；提交确认超时后沿用当前有效计划与原有 Git 模式，普通模式执行 commit + push，用户明确要求 commit-only 时才仅本地提交，不扩大计划文件、目标分支或原流程的其他操作边界。
- R10：Brief 超时默认按完整展示且仍有效的方案进入实现；检查问题处置超时默认修复当前报告全部待处置问题并重新检查，遇到新的业务取舍时暂停。
- R11：Codex 与 Claude Code 在接入能力校验通过时默认开启超时策略，无需每次会话重新启用；提供项目级关闭开关，并保留各确认类型独立调整和关闭的能力。用户主动打开新会话后沿用配置，但只创建本次会话的新待决事项，不恢复旧事项。
- R12：首版为 Codex 与 Claude 提供统一的前台会话启动入口和等待协议，统一计时、人工取消、一次性决定与退出处理；平台差异集中在接入层，新增 Harness 需要完成能力验证。原生启动命令仍可使用，缺少有效受控接入时保留人工确认，不宣称任意 Harness 都已获得自动继续能力。

## Acceptance Criteria

- [x] AC1（R1）：Brief 正文 1000 / 1001 字对应 100 / 130 秒；检查 1 / 2 条待处置问题对应 100 / 130 秒，无待处置问题不等待；提交确认等待 200 秒。三类策略可独立调整或关闭，互不覆盖。
- [x] AC2（R2）：无适用授权时保持人工确认；有授权时展示当前默认动作，并在等待时间届满后无需额外输入即可继续。
- [x] AC3（R3）：用户在自动选择前回复、暂停、取消或更改方案，旧默认动作不执行。
- [x] AC4（R4）：关闭主会话后待决事项取消；原截止时间到达时不会启动或恢复对话，手动重开也不会补跑。
- [x] AC5（R5）：执行已开始时退出，结果可区分已完成、已中断和待核验，不将已完成动作报告为未发生。
- [x] AC6（R6）：Codex 与 Claude Code 分别通过人工选择、超时继续及退出取消的实际验证；其他 Harness 保留人工确认。
- [x] AC7（R7）：人工输入与截止事件竞争、重复通知及工具重试均不会让同一事项重复执行，记录可追溯实际选择来源。
- [x] AC8（R8）：方案变化使旧选择失效；进入检查修复或 Git 动作后仍执行对应流程规定的验证。
- [x] AC9（R9）：提交确认超时沿用当前有效计划的 commit + push 或 commit-only 模式，不擅自切换为本地提交，不扩大计划范围；其他 Git 预检和失败恢复行为保持原合同。
- [x] AC10（R10）：Brief 超时进入对应方案的实现；检查超时修复当前报告全部待处置问题并重检，出现新的业务取舍时暂停，不能将未解决问题直接记录为已接受风险。
- [x] AC11（R11）：在具备有效适配的 Codex / Claude Code 中默认开启，无需逐会话启用；项目关闭或单类关闭时回到人工确认。手动新开会话可沿用配置，不能补跑上次会话的待决事项。
- [x] AC12（R12）：Codex 与 Claude 的统一入口分别通过无人输入时等待到期继续、人工输入先撤销默认决定、关闭入口取消的实际验证；记录方案展示、工具等待、返回状态及后续模型处理，不能用模型轮询成功代替等待调用返回。强杀入口、手动重开与长时间等待单独验证，原生后台实验保留为方案取舍证据。

## Non-Goals

- 不在主会话退出后无人值守恢复执行，不保留用于补跑旧确认的唤醒任务。
- 不给 Spec 的证据不足或业务歧义自动指定答案。
- 不把超时默认决定记录为用户已经人工点击或回复确认。
- 不因通用规则已分发就宣称所有 Harness 都已获得自动继续能力。
