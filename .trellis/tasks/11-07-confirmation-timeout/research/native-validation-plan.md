# 原生后台终端隔离验证计划

## 目标与边界

实际执行状态与时序见 [native-background-results.md](native-background-results.md)。下文是验证计划，不表示所有后续场景已经通过。

- 使用本机已安装的 Codex 0.167.0、Claude Code 2.1.293，验证后台任务结束能否让空闲的原主会话自动继续。
- 原启动方式指用户直接使用原有 `codex` / `claude` 或已有 IDE 入口；本轮不引入 Flower 产品启动器。隔离探针的 PTY 驱动只用于观察真实 CLI，不作为产品运行前提。
- 所有模型响应由本机回环 mock 服务生成，不向真实模型服务发送推理请求，不使用真实凭据。
- 当前 Trellis 任务保持 `planning`；只编写和运行研究探针，不实现产品功能，不启动当前真实用户线程。

## 第一轮：最小自动续接

1. mock 返回真实工具列表中已有的终端调用，启动等待 3 秒后仅输出固定标记的 Python 程序。
2. 必须确认宿主实际返回了后台任务 / session 标识，不能是前台等到命令结束。
3. 下一次主请求返回最终等待文本，不调用 `write_stdin` / `TaskOutput`。
4. 确认等待文本已出现在真实 PTY，然后至少观察 8 秒，无人工输入。
5. 自动续接通过必须同时具备：真实后台任务结束、原生完成事件作为新增上下文交付、最终文本结束之后的新主请求，以及相应回执出现在原主会话。
6. HTTP 重试、辅助模型请求、状态刷新、API 帧到达或任务列表变化都不能单独算作续接成功。

## 后续场景

| 场景 | 观察要求 |
| --- | --- |
| 人工回复先于到期 | 记录原生输入事件与后台完成事件的顺序，确认能在默认动作开始前撤销旧决定 |
| 正常退出 | 截止前退出专用实验会话；到期后没有新模型请求或默认动作 |
| 关闭 PTY / 强杀 | 不能依赖正常 SessionEnd 一定到达；检查是否还有通知交付、模型请求或可被误消费的旧事项 |
| 手动重开实验会话 | 不能因旧任务记录、stopped/completed 通知而补跑旧动作 |
| 临界竞争 | 输入在截止之前、同时、完成通知排队后分别测试，区分后台完成与动作开始 |
| 长于两分钟 | 短场景通过后再验证 100 / 130 / 200 秒及相关宿主资源上限；不拿短场景代替默认时长验收 |

## 证据与清理

- 记录 CLI 版本、测试模式、回环 provider、关键时间、工具名、与固定标记有关的新上下文及退出状态。
- 不保存完整系统提示、请求 header、认证材料或用户配置原文。
- 每个探针有总超时，并清理自己拥有的 mock server、PTY 与子进程；不使用模糊进程名批量清理。
- Codex `--no-daemon` 仅用于隔离实验进程，不能据此声称默认共享 daemon / IDE 模式已经验证。
- Codex 独立 App Server 的专用 Unix socket 对照同样不等价默认 managed daemon；不通过删去 --no-daemon 就宣称测过默认模式。
- Claude 的 bare / stream-json 模式若用于排障，须单独记录，不能伪装成普通 TUI 的相同证据。
- 不修改 `HOME`、`home`、`CODEX_HOME` 或用户全局配置；优先使用已核实的单次 CLI 配置与允许隔离的专有目录。
- 若原生路径不通过，保留失败证据并回到设计取舍，不自行新增启动器、伪造回调或降低原验收要求。
