# 改进版本规划与多人任务协作 Skill 链路

## Goal

参考 `~/project/xhgj-ai-harness-poc` 的实际分工与重规划，让版本规划、PRD 提取和任务校验形成可直接用于多人及 Agent 协作的交付、责任、依赖与验收约定。

## Background

用户要求借鉴已有明确分工的变更，优化 `plan-version` 及相关 Skill。参考案例经历过三人职责分工、人员交接及单负责人使用 Agent 的工作包重规划。已有对话明确区分 Wave 业务交付与 Task 工程完成；详见 [案例与差距分析](research/case-analysis.md)。

当前三个 Skill 已限制碎拆，但存在两处断点：拆分规则没有稳定区分工程工作包与业务闭环；人员分工在拆分之后形成，且交接、容量和集成责任未完整传给单 Task 与规划校验。

## Requirements

### R1：交付层级和任务粒度

- 版本表示完整需求范围；Wave 以业务操作及其可验收结果定义，形成可统一提测／交付的业务批次；Task 表示上下文连贯、有明确输出和验证条件的执行工作包；内部步骤使用 Checklist。
- 用户本轮明确 Wave 应与业务操作挂钩。每个 Wave 必须能说明业务角色、起始条件、操作过程、最终结果和验收依据；先识别操作与结果，再确定工作包和人员分工。
- Wave 可包含围绕同一结果的多个操作；粒度以有实际业务意义、能停下来验收的结果为依据，操作按钮数、人员数或技术层数不决定 Wave 数量。共享技术准备作为服务于业务 Wave 的前置工作包。
- Task 不要求每包都独立提供完整用户体验；有明确提供方、消费方、稳定交接和工程验证时，允许按实际技术职责分工。
- 人员、技术层、页面、接口或字段本身不构成新建 Task 的充分理由。能在一个工作包内完成的细节不自动复制成持久子任务。
- Task 的实现、检查和合入证据与 Wave 的集成、真实业务验收分别记录；沿用既有生命周期与审批规则。

### R2：能实际执行的协作规划

- 拆分前读取团队职责、技能、可用投入和协作方式；未明确的信息标为待定，不假定每人全职或开发速度相同。
- 工作包说明主要负责人、协作者、代码／仓库边界、输入输出、消费方、依赖交付内容、工程验证及所属 Wave 的集成验收责任。
- 区分凭契约／Mock 可开工、真实服务具备可联调、业务条件齐备可验收；只阻断依赖该条件的工作。
- 根据共享文件、契约稳定性、评审／指导／联调成本和人员容量编排并行及接力；不通过人数或任务数直接换算交付日期。
- 用户明确要求按工时而非人天估算：新计划默认使用小时（h）区间，按当前人和 Agent 的协作方式估实现、自测、联调与验收修复；不将原人工人天机械换算成当前小时数或套用固定 AI 提速倍率。
- 时间表说明作业耗时与人工投入的口径，Agent 自主运行和外部等待分别说明，重叠活动不重复计入合计。缺少实耗记录时标注待估／区间依据及下一检查点，不用任务创建到完成的日期差冒充开发工时。
- 支持多人按职责协作和单负责人使用 Agent，不预设固定团队角色，也不要求一个 Task 只能由一名执行者参与。

### R3：规划、提取与校验连续一致

- `trellis-plan-version` 输出上述分工与交接依据；`trellis-extract-prd` 在已确认边界内继承；`trellis-verify-task` 对规划与已创建的相关任务、子任务一起检查。
- 原始业务需求及 UI 原文继续逐条追溯；基于已确认范围形成的工程验证和协作责任单独说明依据，不能伪装成需求原文。
- 校验可识别责任缺失、重复范围、共享修改冲突、循环或没有交付内容的依赖，以及无人收口的 Wave 验收。
- 不能因版本规划写了“允许拆分”就豁免工作包输出、验证与集成检查，也不能把所有有交接的技术分工都判为业务碎拆。

### R4：实际开发中的调整与兼容

- 允许远期范围滚动细化；用户明确要求全版本建 Task 时按已确认范围创建，不自动省略远期任务或自动把候选全部物化。
- 重新分工时保留来源需求、稳定标识、已完成范围、历史交付人和证据；以实际缺口重估，不沿用过期日期或用未关闭卡片数计算剩余工作量。
- 旧产物缺少协作信息时报告待补充或证据不足，不编造人员、截止日、依赖或完成事实；正常跨日期补建任务不触发无必要的目录改名。
- 优先扩展现有三个版本文档和任务文档；协作细度按实际参与者、依赖与风险裁剪，不强制增加多份同源台账。

### R5：持久维护与分发

- 本轮改动以 0.6 的 `trellis-plan-version`、`trellis-extract-prd`、`trellis-verify-task` 为一个协同交付；同步 `.agents` 与 `.claude` 入口、发布快照和本项目受管副本。
- 既有 Brief 的 `Context & Decisions` 承接交接信息；不新增固定 Brief 栏目或修改其首次实施批准规则。
- 案例仅用于提炼决策规则和中性示例，不把参考项目的人名、仓库路径、时间或外部地址写成通用 Skill 的固定要求。

## Acceptance Criteria

- [x] AC1（R1）：Wave 可追到业务角色、起始条件、操作过程、结果与验收依据；对“费用接入 → 审核运行 → 页面联调”的案例，三个 Skill 一致识别工作包输出与 Wave 业务验收；有契约验证的服务工作包不被要求独立完成全链路。
- [x] AC2（R1、R2）：多人前端／后端／工作流协作和单负责人使用 Agent 两种场景，均能回答谁做、交什么、谁接、何时能开工／联调、谁收口；不按角色或人数机械增建任务。
- [x] AC3（R2、R3）：工时以小时区间和明确口径表达；能识别人工／Agent／等待混算、同一人容量重复、共享契约冲突、依赖缺交付和 Wave 缺少验收责任；无实耗数据时不编造小时数。
- [x] AC4（R3）：实际子任务被额外碎拆或重复承接范围时会被发现；合法工程验证与原始业务 AC 保持可追溯且互不替代。
- [x] AC5（R4）：对人员替换、有部分完成证据、旧字段缺失、滚动规划和显式全量创建场景，分别保留历史、报告缺口、遵循创建范围；不重写历史完成状态或强迫重命名目录。
- [x] AC6（R5）：源文件、平台副本、快照及受管安装结果一致，规则专项、产物和输出模板验证通过；无审批边界或执行模式变化。

## Out of Scope

- 不修改参考项目的规划、任务或业务代码，不执行 GitLab 写入、部署、付费实验或人员通知。
- 不新增协作调度器、任务状态、Task JSON schema、依赖图运行时或分工专用 Skill。
- 不改动通用 workflow、brainstorm、route、Check-All、Brief 的状态和批准规则，不修改冻结的 old／0.5 变体。

## Technical Notes

- 实施入口为 `vendor/skill-garden/.trellis/0.6/{.agents,.claude}/skills/<skill>/SKILL.md`；维护与同步顺序见 `design.md`。
- 用户在完整 Brief 展示并明确 Wave 业务操作边界后回复“是的 按照我们 ~/project/xhgj-ai-harness-poc的经验教训，来改造吧”，批准本任务实施；证据边界和场景验收详见研究材料。
