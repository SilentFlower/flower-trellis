# Flower Trellis 安装与版本监控

## Goal

在不破坏 `ai-fund` 现有公开 Flower Trellis 介绍页的前提下，为管理员提供安装设备、开发者别名、Flower/Trellis 版本和最近活跃时间的运营视图，用于判断版本覆盖、升级滞后和活跃安装规模。

## Background

- `ai-fund` 已有公开路由 `/trellis` 和公开接口 `GET /api/flower-trellis/meta`，用于展示 npm/GitHub 实时元数据。
- `ai-fund` Worker 已有 `isAdminRequest(request, env)`，以登录 token 中的 `name` 与 `env.ADMIN_NAME` 比对；管理员数据必须继续由后端鉴权，前端显隐不能作为安全边界。
- `flower-trellis` CLI 可读取自身版本、捆绑 Trellis 版本、目标项目版本，以及目标项目 `.trellis/.developer` 中的开发者别名。
- 仅执行 `npm install -g flower-trellis` 时没有可靠的项目和开发者上下文，因此本功能统计的是“启用上报且至少运行过一次 CLI 的活跃安装”，不是 npm 下载量或绝对安装量。
- Flower 现有联网契约是尽力而为、带超时、失败不阻断主流程；遥测上报必须继承该边界。
- Codex/Claude Code SessionStart hook 已周期性调用 `flower-trellis self-check --json`；`self-check` 复用 `updateCheck.intervalHours` 缓存，只有缓存失效时才执行真实远端版本检查，适合作为低频上报触发点。
- MAC 地址可能因多网卡、VPN、虚拟机、容器或地址随机化而变化，也属于敏感持久标识，不适合作为 Flower 安装实例的主键。

## Requirements

- 现有 `/trellis` 公开介绍内容对非管理员保持不变。
- 现有 `/trellis` 页面为管理员显示“产品信息 / 安装监控”两个 Tab；非管理员保持原页面结构且不显示监控入口。所有监控明细和聚合查询必须由 Worker 后端执行管理员校验，未授权请求返回 `403`。
- 每个安装实例使用保存在当前操作系统用户配置目录中的随机 `device_id`；该标识应跨 Flower 升级和 npm 重装保持稳定，不采集设备序列号、MAC 地址、主机名、项目绝对路径、仓库地址或操作系统用户名。
- API 与数据库统一使用字段名 `device_id`，管理页面显示为“设备 ID”并使用短格式；README 明确它是 Flower 随机标识，不是物理硬件编号。
- 开发者身份使用目标项目 `.trellis/.developer` 中的自报别名；字段允许为空，不要求钉钉授权或实名绑定，同一安装实例可在不同时期关联多个开发者别名。
- 上报字段应限于实现运营目标所需的最小集合：`device_id`、Flower 版本、捆绑 Trellis 版本、项目版本（存在时）、开发者别名（存在时）、平台/架构、事件类型和客户端时间。
- 服务端负责生成权威接收时间，并维护首次出现、最近出现和上报次数；界面使用“最近活跃/久未上报”，不得显示无法证明的“在线/离线”。
- 活跃状态由服务端根据 `last_seen_at` 统一派生：7 天内为“最近活跃”，8 至 30 天为“久未上报”，超过 30 天为“长期未活跃”；前端只消费状态结果，不重复定义阈值。
- 服务端保存每台设备的当前状态；仅当 Flower 版本发生变化时写入一条版本历史，记录旧版本、新版本和服务端变更时间，普通心跳不写历史。
- 管理员视图至少提供设备数、开发者数、最近活跃数、版本分布，以及可按开发者、版本和活跃状态筛选的安装明细。
- 第一版管理员视图保持只读，仅提供聚合、查询、筛选和版本历史查看；不提供删除、归档、忽略、远程更新或其它设备管理操作。
- 常规上报复用自动版本检查链路：仅在 `self-check` 或 `init/update` 实际执行远端版本检查时发送一次，不为每条 CLI 命令增加独立心跳。
- `self-update` 或项目更新成功后补发一次即时上报，使管理端无需等待下一个检查周期即可看到新版本。
- 上报必须短超时、失败静默降级且不影响 `init`、`update`、`self-update` 等主流程的成功或退出码。
- 自动版本检查与安装状态上报复用调度周期，但使用独立配置：`updateCheck` 只控制版本检查，`telemetry` 只控制状态上报。
- `telemetry.enabled` 默认开启；新安装和升级后的既有安装在缺少显式配置时均按开启处理。
- 遥测在 CLI 运行时保持无感知：不弹确认、不打印首次说明、不改变现有命令输出，也不为等待上报延长主流程；客户端仍必须提供状态查询、关闭和重新开启能力，并支持专用环境变量临时关闭。
- README 使用简短段落披露遥测默认开启、主要采集字段、不采集的敏感信息和关闭方式；不新增运行时提示或独立长篇隐私页面。
- 公网上报入口必须做严格字段白名单、长度限制、枚举校验、请求体大小限制和频率限制；匿名数据只能作为运营参考，不能作为审计证据。

## Out Of Scope

- 监控仅安装但从未运行 CLI 的设备。
- 静默采集硬件指纹、网络地址或项目源码信息。
- 实时在线状态、远程控制、远程执行升级。
- 第一版建立完整的项目清单或保存每次命令的详细行为日志。
- 将自报的开发者别名视为经过钉钉认证的实名身份。

## Acceptance Criteria

- [ ] 非管理员访问 `/trellis` 时保持原公开内容且看不到安装监控 Tab，直接调用管理员查询接口得到 `403`。
- [ ] 管理员访问 `/trellis` 时可在“产品信息 / 安装监控”两个 Tab 之间切换。
- [ ] 管理员可查看设备/开发者/版本聚合和分页明细，并按开发者、版本、活跃状态筛选。
- [ ] 管理端及 Worker 不暴露设备删除、归档、忽略或远程操作入口。
- [ ] 7 天、30 天边界前后的设备状态由服务端稳定计算，聚合统计与列表筛选使用同一口径。
- [ ] 同一 `device_id` 重复上报时更新最近活跃和当前版本，不重复计为新设备。
- [ ] API、数据库和管理端使用一致的 `device_id` 语义，完整值不在列表中直接铺开显示。
- [ ] Flower 版本未变化的重复上报不新增历史；版本变化时只新增一条包含旧版本、新版本和服务端时间的记录。
- [ ] 自动版本检查命中本地缓存时不重复上报；缓存失效并真实联网检查时最多上报一次。
- [ ] 完成自更新或项目更新后，管理端可在即时上报成功后看到新版本。
- [ ] 上报请求失败、超时或服务端不可用时，Flower CLI 原命令仍按既有行为完成。
- [ ] 服务端拒绝超长字段、未知字段、非法版本/平台/事件值和超限请求体。
- [ ] 数据库和接口不保存主机名、MAC、设备序列号、项目绝对路径、仓库地址、操作系统用户名或原始 IP。
- [ ] 缺少 `telemetry` 配置时默认允许上报；首次及后续上报均不产生 CLI 提示或交互。
- [ ] 客户端可查看当前上报状态、关闭后续上报并重新开启；关闭版本检查不隐式修改上报设置，反之亦然。
- [ ] 遥测请求不改变现有命令 stdout/stderr 契约，也不造成用户可感知的额外等待。
- [ ] README 包含简短遥测说明，并给出查询与关闭方式。

## Notes

- 该任务跨 `flower-trellis` CLI、`ai-fund` Worker/D1 和 Vue 页面，属于复杂跨仓任务。
