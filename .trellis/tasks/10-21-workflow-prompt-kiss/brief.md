# Brief — 精简默认工作流与提示词，保留关键交互能力

## Goal

- 让默认开发与收尾流程少停顿、少读重复规则，同时保留必要的审查与确认能力。

## Scope

- 统一检查通过后自动收尾的指令；没有执行偏好时默认当前会话完成实现和检查。
- 精简轻量检查的必读材料与通过报告，收敛问题分类的重复说明。
- 精简 Update-Spec 入口，将 Push 的特殊流程按需加载，复用未变化的模板。

## Non-Goals

- 保持现有 Brief 的文件、内容结构、用途和审批规则。
- 保持 CHK/FBK/DOC 编号与分区、升级门禁以及 Git 精确计划的一次确认。
- 本轮不增加工作流、状态文件或配置体系，不涉及 CI 重构、发版及其他项目升级。

## Technical Overview

- 修正无任务状态中残留的等待条件，检查通过后沿既有链路自动进入规范评估和提交计划。
- 在现有路由解析末尾增加 inline 缺省，统一普通执行、无任务路径及自动循环预检；明确指定和既有偏好继续优先。
- 保留检查维度、必要验证和 full 升级条件，按实际场景加载 DOC、问题处置和自动循环细则；轻量通过只展示有用结论与证据。
- Update-Spec 通过现有 Patch 就地去重；Push 使用现有引用目录承载多仓、merge、GC 和恢复细则，再同步各平台与生成结果。

## Context & Decisions

- 用户本轮要求优化流程、提示词和 skill；现有 Brief 能帮助理解 AI 如何修改，保持现状。
- 自动收尾推进到提交计划，实际 Git 操作继续等待该计划的确认。
- 问题分类有直观识别价值，保留；通过删除重复指令和缩小默认读取范围降低负担。

## Risks

- 精简时可能漏掉异常或平台分支；以能力保留断言、引用完整性及原生平台回归验证。
- 内置缺省只适用于正常空状态，损坏记录、授权问题或明确子 agent 无法执行时继续保留诊断与停止边界。

## Acceptance

- 检查通过后不再额外等待“继续”；无模式设置时实现和检查均不弹菜单。
- 轻量检查及普通收尾的默认控制文本实际减少，有问题时分类与证据完整，原有必要验证和安全边界有效。
- Brief 与升级策略保持现状，源、快照、平台结果一致，相关本地回归及推送后的原生 CI 通过。

## Next Step

- Brief 获确认后启动任务，先统一自动收尾指令与路由缺省，再精简检查和收尾提示词。
