# Brief — 批量更新多个 Flower 项目

## Goal

- 用一次命令更新集中目录和零散路径中的多个 Flower 项目，省去逐项目重复升级。

## Scope

- 新增 update-all，组合使用重复的 --root 和 --target，并提供 --dry-run 与 --yes。
- 逐项目预检、更新和汇总；同步根帮助、命令帮助、README、自动测试及跨平台 CI 清单。
- 更新成功后提示各仓库分别进入 Git 确认流程。

## Non-Goals

- 不扫描未指定的文件系统位置，不建立全局项目注册表。
- 不修改项目应用版本，不自动提交或推送 Git，不做跨项目原子回滚。

## Technical Overview

- 在指定目录内发现有 Flower 安装证据的项目，按真实路径去重；写入前读取版本、Git clean 状态和活动任务。
- 远端版本只查询一次；如需升级，全局 CLI 只安装一次，再顺序调用现有完整项目 update 链路。单项目失败记录后继续，最终按项目输出状态与退出码。
- 预览保持零写入；远端不可用时注明未确认最新版本，仅追平到当前已安装 CLI。

## Context & Decisions

- 现有 self-update 是单目标入口，保持其参数和行为兼容；新增独立 update-all。
- 用户项目既集中又分散，因此目录扫描和显式路径可以混用；显式批量命令以 --yes 授权写入，脏工作区或活动任务默认跳过。
- 同一 Git 仓库中的多个项目共用写入前的 clean 判断，避免批次自身产生的变更误阻断后续项目。

## Risks

- 全局安装后必须由新 CLI 核对实际版本，否则旧进程状态可能误导项目更新。
- 同一 Git 仓库若被外部进程同时修改，批量命令无法提供跨进程事务隔离。
- 新 CLI 命令需在 Ubuntu 和 Windows 的更新链路 CI 中实际通过后才能完成跨平台验收。

## Acceptance

- 组合输入可发现并去重项目；无效目标、脏工作区和活动任务有明确结果。
- --dry-run 对 CLI、项目和更新缓存零写入；真实执行缺少 --yes 时拒绝。
- 全局安装最多一次；项目失败不阻断其他项目；未全部完成时返回非零并汇总逐项原因。
- 离线时只追平本机版本且明确说明远端未确认；不产生应用版本修改或 Git 提交、推送。
