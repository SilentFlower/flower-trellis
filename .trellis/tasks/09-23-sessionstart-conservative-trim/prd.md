# 保守精简 SessionStart 开场注入并保留流程约束

## Goal

保守精简 Trellis SessionStart 的常驻上下文，减少普通重复和当前场景无关的信息，同时保持模型可发现并执行原有流程约束。

## Scheduling

- 用户于 2026-09-23 要求先建档，等待 `09-22-task-close-archive-gc-refactor` 和
  `09-20-auto-loop-in-progress-baseline` 完成后再推进；两项关联任务现已完成并推送，延期条件已满足。
- 本任务已在最终依赖代码上恢复规划并重新测量基线；与前序任务不建立父子关系，也不修改其生命周期或
  auto-loop 行为。
- 状态继续保持 `planning`，直到技术设计、实施计划和 Brief 经用户确认；确认前不运行
  `task.py start`，不进入实现。

## Background

- 用户报告此前精简过度曾导致模型漏流程。本次只处理已讨论的五项内容，不进行整体工作流重写。
- 历史回归包含关键动作被压弱，以及规则虽存在但实际请求入口无法到达；静态文字存在不能替代行为验证。相关证据与代码入口见 `research/context-estimate.md`。
- 在前序任务最终代码上，同口径隔离测量的 Codex＋Astra、无活动任务、未触发更新场景仍为
  19,177 UTF-8 字节；控制面合计为 108,611 字节。按候选文案预计减少 1,089 字节，约 5.68%。
  这是估算，不是已实施结果，不作为必须达到的压缩指标。

## Requirements

### R1. 删除普通重复说明

- 删除开场 `<ready>` 中重复的“上下文已加载、遵循 task-status、按需读详情”说明，保留现有状态与加载入口。
- 删除 `Guardrails` 中重复的 PRD-only 说明，保留 `Planning Artifacts` 中对轻量和复杂任务的完整要求。

### R2. 按当前平台裁剪说明

- Phase 1.3 的长平台名单改为明确行为要求：使用子代理时派发前配置任务上下文，inline 执行跳过。
- 开场派发说明只携带当前平台适用的内容；共同协议必须继续覆盖全部子代理，包括研究代理。
- 派发提示的 `Active task: <task.py current 返回的路径>` 前缀、实施和检查先进入 `trellis-route`、Codex 原生注入及子代理主动读取兜底继续保留。
- Grok、Kimi 等平台保留各自的调用要求；平台依据来自实际平台入口，无法识别时保留完整说明，不能靠模型自行忽略不适用段落。
- 只调整说明的呈现与加载范围，不改变执行模式选择或派发行为。

### R3. 移走编号历史说明

- 从常驻开场移走“为什么没有步骤 3.1”的历史解释。
- 保持阶段编号、执行顺序和阶段详情加载入口不变。

### R4. 更新处理规则按事件注入

- 从常驻跨阶段说明中移走更新确认的处理顺序规则。
- 检测到可处理的更新或项目版本不同步时，动态更新上下文应完整说明更新展示、确认、执行、暂缓或跳过，以及与普通请求的处理顺序。
- 更新成功后的结果提示继续引导进入 `trellis-push`；确认和已有授权语义保持不变，不自动扩大用户授权。
- 无更新时不额外注入更新处理流程；归属表中原有入口索引仍保留。
- 更新摘要原本已按条件注入，不能将其重复计作本任务新增节省。

### R5. GC 仅保留本次结果提示

- 从常驻跨阶段说明中移走“三天后整理已关闭任务”等内部机制介绍。
- GC 的执行程序、触发条件、归档路径、本地提交及延后规则沿用前序任务最终结果；本任务不修改这些行为。
- 实际整理、延后或异常时继续报告必要结果，无动作时不追加机制说明。

### R6. 保护流程约束

- 完整归属表及其运行时脚本列保持不变。
- `Request Triage`、`no_task` 的现有关键规则保持不变。
- 保留规划与实施的授权边界、实施后检查、检查后停止或继续条件、提交入口、auto-loop 的有效授权和返回规则。
- 保留父子任务规则、规划产物职责、完整阶段导航、必读规范入口和详情加载命令。
- Astra 专属提示、workflow-state 条件注入与心跳机制保持不变。
- 维护现有 `state / rules / stages` 分段边界及并行无顺序依赖契约，不改变 `### Planning Artifacts` 的分段锚点。

## Acceptance Criteria

- [ ] AC1（R1）：实际开场输出不再包含两处选定的普通重复说明，状态、产物要求与读取入口仍完整。
- [ ] AC2（R2）：已识别平台只收到适用说明；共同协议、平台特有要求和未知平台完整回退均可验证。
- [ ] AC3（R3）：编号历史说明退出常驻开场，阶段导航与详情加载保持可用。
- [ ] AC4（R4）：无更新、需要确认、暂缓或跳过、更新成功四类路径保持正确顺序及授权边界。
- [ ] AC5（R5）：GC 执行行为不受影响，实际动作、延后和错误诊断保留。
- [ ] AC6（R6）：被保护的规则、归属表、模型提醒、心跳和分段契约没有意外删改。
- [ ] AC7：在同一最终代码基线和固定场景下测量修改前后的真实注入，分别报告普通开场、更新事件和各平台结果；说明字节与 token 的区别，不抬高预算掩盖增长。
- [ ] AC8：验证历史易回归路径：无任务的项目规范发现、planning 收到无关请求、实施后进入检查、直接 push、交互式检查停止、auto-loop 返回，以及 compact 后恢复。
- [ ] AC9：分别记录结构与入口验证、实际模型对话验证的证据及限制，不能以规则文字存在或注入成功宣称行为可靠。
- [ ] AC10：源 Patch／源资产、生成目标、快照和部署结果按各自所有权保持一致，相关测试与上下文预算检查通过。

## Non-Goals

- 不整体重写工作流，不压缩关键规则，不删归属表列，不新建通用流程控制器。
- 不修改任务 Close/GC、auto-loop 或另一窗口正在修复的功能行为。
- 不增加每轮注入，不移除模型专属提醒，不调整预算阈值。
- 不以必须节省 1,089 字节或某个百分比作为交付硬指标。
- 未经后续流程授权不发布、不提交、不推送。
