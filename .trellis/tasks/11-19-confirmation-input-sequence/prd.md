# 以输入事件序号统一 Claude 与 Codex 自动确认

## Goal

让 Claude 与 Codex 在普通人工回合、子代理回传后的主会话及原生恢复回合中，都能依据当前会话和后续输入变化准备自动确认，消除对历史真实用户消息 ID 的硬性依赖。

## Background

- 用户已明确要求以宿主输入事件和会话内递增序号判断等待是否失效，并将 Claude 与 Codex 纳入同一任务。
- 已在 `cnooc-virtual-mall-data` 的 Claude 会话 `8bd8489a-d726-4bd0-942d-74db8da07610` 复现准备失败：调研子代理回传的当前回合标记为 `peer`，Hook 将其 ID 写入人工基线，后续日志校验排除该来源，返回“当前回合缺少可核验的完整记录”。
- 该会话日志约 1.8 MiB。此前针对 32 MiB 尾部搜索窗口的猜测已被本次证据更正。
- 可追溯证据集中在 [现场取证与源码定位](research/input-baseline.md)，包括原始日志第 304、380、381 行和运行时入口。

## Requirements

- R1：Claude、Codex 的自动确认准备均取消“必须定位历史真实人工消息 ID”的前置条件。
- R2：准备时冻结会话内的输入事件序号；准备、等待、派发、领取和开始执行期间的新用户输入或中断，使旧许可失效。
- R3：主会话收到子代理回传或原生内部唤醒后可以准备新确认；事件来源独立处理，子代理消息不取得用户授权。
- R4：保留当前会话与原窗口绑定、完整方案展示后计时、材料变化失效、精确原生唤醒核验和单次领取/执行。
- R5：升级、取消后重新准备、连续确认替换及跨进程续接，统一使用当前有效输入序号与本次请求；旧请求不得重新执行。
- R6：同步受影响的源码、分发协议、测试与项目规范；以真实来源报告故障阶段。

## Constraints

- 当前回合、原窗口、队列通知和请求回执各自保留必要身份核验；本次取消的门槛是历史真实人工消息 ID。
- 普通人工回合、peer 回传后的主会话和恢复回合使用同一输入失效规则；真实用户消息正文不承担机器授权凭证职责。
- Linux/WSL 与原生 Windows 沿用既有支持范围；Node 18.17+、Python 3.8+ 基线保持现有约定。
- 本任务属于确认机制自身开发，按现行协议设置 `confirmationTimeoutDisabled=true`，使用人工阶段确认。隔离验收仍覆盖自动链路。

## Acceptance Criteria

- [x] AC1（R1、R3）：两端在普通回合及子代理回传后的主会话均可准备确认，且无需历史真实人工消息 ID。
- [x] AC2（R2、R4）：在准备、展示、倒计时、派发、领取及 started 的竞争位置注入新用户输入或中断，旧等待和未启动许可均失效。
- [x] AC3（R3、R4）：子代理消息、工具结果和无关上下文保持各自来源；真实内部通知能续接；人工伪造提醒不取得许可。
- [x] AC4（R4、R5）：完整展示、原窗口退出、材料变化、重复领取、重复 started、取消后重建与旧提醒恢复均保持既有可观察行为。
- [x] AC5（R5、R6）：升级兼容、跨进程续接和两端原生验证均有证据，源码与分发内容保持一致。

## Out of Scope

- 本轮范围聚焦确认运行时的输入识别；人工风险接受策略、Git 停止条件和倒计时配置保持现有契约。
- 外部业务项目升级、软件发版和生产部署由各自后续流程承接。
