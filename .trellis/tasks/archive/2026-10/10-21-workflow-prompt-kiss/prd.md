# 精简默认工作流与提示词，保留关键交互能力

## Goal

减少 Flower/Trellis 默认开发与收尾路径中的多余停顿、重复提示词和特殊场景负担，同时保留用户理解方案、区分问题及确认关键操作的能力。

## Background

- 用户明确把本轮 KISS 优化限定为流程、提示词和 skill，并同意新建任务。
- 当前存在状态提示与主流程的继续条件不一致、无模式时要求菜单选择，以及轻量路径加载完整处置细则等负担；证据与实际文本基线见 `research/flow-audit.md`。
- 用户要求保持现有 Brief，保留 CHK/FBK/DOC 的直观分类及现有升级门禁。

## Requirements

- R1：检查通过后默认同轮推进规范评估与提交计划，不额外等待“继续”；用户明确停止、未处置问题和必要决策仍按现有规则处理。
- R2：正常缺少当前模式、有效既有选择、个人默认和 runner 候选时，实现与检查直接在当前会话执行；明确指定、个人默认和主动重选继续有效，异常上下文不借缺省绕过诊断与授权边界。
- R3：轻量检查按受影响范围执行，减少必读说明与固定报告负担；必要验证、证据复用和升级 full 的条件保持有效。
- R4：CHK 主路径、FBK 兜底、DOC 事实漂移的编号与分区保持可一眼区分；收敛重复分类说明。
- R5：规范评估使用精简入口，提交中的特殊流程与详细模板按需加载；保留现有结果和安全边界，已读且未变化的材料可复用。

## Acceptance Criteria

- [x] AC1：无额外停止条件的通过路径直接进入规范评估与提交计划；任务与无任务入口语义一致。
- [x] AC2：无模式设置时实现和检查均无需菜单交互；既有偏好、明确覆盖与主动重选符合用户选择。
- [x] AC3：普通轻量检查只加载当前路径必要材料，正常通过报告包含范围、结论、实际验证、必要风险和下一步。
- [x] AC4：问题分类、风险接受、DOC 自修边界、必须验证和 full 升级规则无功能回退。
- [x] AC5：规范评估和提交仍使用现有完成链协议；精确文件范围、一次 Git 计划确认和异常现场保留有效。
- [x] AC6：相对研究记录中的基线，默认 light、inline、规范 no-op 与普通单仓 Push 路径的控制文本实际减少，全部关联材料不因拆分重复增加；受影响平台与生成结果一致，针对性回归通过。
- [x] AC7：Brief 与升级相关作者源保持现状，相应保护能力回归通过。

## Non-Goals

- 不调整 Brief 的文件、结构、用途或审批规则。
- 不改变现有升级优先提示、处置与确认策略。
- 不合并 CHK/FBK/DOC 分类，不另建轻量工作流、状态机或配置体系。
- 不扩展到 CI 重构、软件发版、其他项目升级或既有 worktree 方案返工。
