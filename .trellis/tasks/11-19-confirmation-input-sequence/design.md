# 自动确认输入事件序号设计

## 目标与边界

统一 Claude、Codex 的准备与失效判断。将“历史真实人工消息身份”从许可前置条件中移除，以当前宿主运行身份、输入事件序号、本次方案和精确请求建立确认。

本任务是一个跨两端的共享运行时交付。两端与共同状态机须一起验收。现有风险接受、Git 条件、默认动作、用户倒计时和权限 owner 保持原契约。

## 现有契约

入口签名继续使用 `prepare / wait / claim / result / status / cancel`。`ConfirmationStore` 沿用目录锁、原子替换、只读观察和状态同步方式。`runtime.CONTRACT_VERSION` 当前为 3；许可结构变化时递增该版本。

`generation` 当前同时承担请求替换和输入失效。新设计保留其请求生命周期用途。新增的输入序号与回合身份分开保存，避免创建新确认本身被判成用户插话。

## 输入与会话快照

以下为拟新增/调整的内部字段，实施时同步所有生产者、消费者与测试夹具：

| 字段 | 作用 |
| --- | --- |
| `inputSeq` | 当前项目、平台、会话及宿主运行内的非负整数输入序号；在同一状态锁内更新。 |
| 请求内冻结的 `inputSeq` | 本请求准备时的输入基线；派发、领取和 started 均与当前值比较。 |
| 当前回合身份 | 绑定最终正文与当前宿主回合，允许 peer、内部通知及恢复回合。 |
| 原生事件/日志观察边界 | 只消费准备期间及之后的新增事件，用于分类、展示和精确唤醒核验。 |

现有 `humanId`、`lastHumanMessageId`、`baselineMessageId` 不再是新许可必要字段。原生事件自带的标识可用于当前事件关联和去重，不能据此恢复历史人工 ID 门槛。

初始化要求宿主来源与会话已经核验。序号可从 0 建立；准备过程不要求历史人工消息存在。窗口生命周期继续沿用 Codex 原窗口绑定与 Claude runId/原生前台身份。

## 宿主适配与事件分类

- 两端统一输出当前会话、回合、输入序号和本次观察证据。共同运行时负责比较与状态转换。
- 新的宿主输入事件与用户中断递增输入序号，并即时取消旧等待或使尚未 started 的许可失效。Claude 的 peer 回传也会触发主会话新回合，按同一规则推进序号；这个序号只表示上下文变化，不表示人工授权。
- peer、工具结果、技能正文和普通上下文分别保留来源。它们不提供人工批准，也不冒充人工输入。
- Claude 的 UserPromptSubmit 同时会承载 peer。适配器使用当前会话的原生来源元数据及新增 transcript 记录分类；Hook 的名字与正文均不足以单独证明输入来源。
- 原生 Hook 先于新增记录落盘时，先以事件序号取消旧等待。疑似自有通知只暂缓取消，许可派发/领取/started 前必须以本次新增记录完成精确分类。不能跳过准备过程中已经发生的真实输入。
- 源数据明确缺失或损坏时报告具体宿主、阶段和证据缺口。正常 peer 来源应进入可准备路径。候选事件尚未落盘按实际进度续读，沿用宿主已有执行预算，不另加历史扫描上限或任意固定等待。
- 主会话处理 peer 后若进入新的展示回合，旧展示许可按输入和回合变化失效；当前回合可依既有自动恢复流程重新准备、完整展示并独立计时。
- Codex 恢复回合使用当前原生回合及宿主状态；准备不再为了寻找人工输入而强制回溯整条恢复链。当前来源、线程归属和日志完整性仍按实际使用处核验。
- 自有后台唤醒仍核对请求 ID、原生 task/queue 身份及事件来源。用户粘贴同样正文按真实人工输入处理。

## 准备与竞争处理

1. 读取当前锁保护的输入序号、宿主运行与回合身份，检查上一执行终态。
2. 冻结本次材料，建立当前日志/事件观察位置。起点服务本次新事件与展示核验，无需定位旧人工消息。
3. 再次观察宿主输入与回合，在写锁内复核输入序号、运行身份、当前回合和请求代次。
4. 条件稳定才创建新请求；其冻结输入序号、材料摘要与展示回合。准备过程中出现新输入时报告准备被打断。
5. worker 在原回合完成且完整正文匹配后启动单调计时。未变化的观察继续使用只读快路径。
6. 派发、claim、started 均在原有检查位置复核输入序号与材料；claim、started 写锁内再次比较。新输入与任一步竞争都不能放行旧动作。
7. started 成功后保持原单次执行及终态记账语义；后续输入不伪称已执行副作用撤销。

当前展示、冻结材料、宿主事件和许可分别承担不同职责。回合/通知 ID 保留必要身份用途，输入取消统一使用序号。

## 状态兼容与升级

- 原状态读写结构的兼容读取保留，新增输入序号执行严格整数校验。旧状态中缺少输入序号不能被解释为旧许可已满足新契约。
- 沿用安装器在确认资产实际更新前取消旧等待的机制；预览和无变化更新维持既有状态。
- 新许可使用新 contract version；旧未开始许可结束后，可在当前有效宿主上自动准备新确认。恢复不要求再查找旧人工消息 ID。
- 已 started 的旧执行保留据实终态记账，原请求和回执不得被新准备覆盖；新契约不重执行业务。
- status、cancel、项目关闭和卸载能够处理升级前后状态；卸载后不重新创建目录。
- 输入序号的持久化与消费采用同一状态锁。跨进程的 Hook、wait、claim、result 观察相同值。

## 作者源与同步

运行时修改 `src/assets/`，平台接入按实际需要修改 Flower 自有 Hook Patch。协议修改 Skill-Garden 作者源后，通过 `npm run sync` 和 compiled-target 工具同步分发，再通过 Plugin 生命周期更新本项目 dogfood。实现不直接以部署文件作为作者源。

任务现场业务仓库只作为只读取证来源。实际给业务仓库升级和软件发版由后续独立流程承接。

## 验证与风险

- 先增加真实 peer 回合、没有历史人工记录、缺少人工消息 ID 的回归；对两端完整 CLI 链路验证 prepare 到终态。
- 竞争测试使用事件屏障，覆盖准备、展示、等待、派发、claim 和 started 前的新输入；验证旧请求失效与单次执行。
- 覆盖 Hook 与日志落盘先后、同回合插话、恢复回合、取消重建、跨进程状态读取、旧通知到达、人工粘贴通知。
- 保留日志替换/截断、窗口退出/重绑、材料变化、任务绑定漂移、预算、Windows 状态锁与原子替换测试。
- 最大交付风险是漏记新输入和错误识别内部通知；通过原生来源核验、锁内复核与故障注入验证。
- 本机制自改任务启用 `meta.confirmationTimeoutDisabled=true`，本任务的 Brief/Check/Push 使用人工确认。隔离验收项目继续验证真实自动确认链路。
