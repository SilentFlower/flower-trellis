# 分离后台确认的回合来源与请求生命周期

## 目标

Codex 与 Claude 在内部通知唤醒的同一回合内，可以可靠地创建、取消及替换后续确认，并保持每个请求独立展示、计时、领取和执行。

## 已确认的问题

- Codex 在准备确认时，仅从当前 `consumed` 请求恢复原始唤醒来源。首次创建新确认会替换该请求，再次准备时触发“队列唤醒来源不符”。证据：`src/assets/flower_confirmation_runtime/codex.py:178`、`:309`，替换发生在 `runtime.py:195`。
- Claude 的通知回合也要求当前请求仍为 `consumed`，并与原始通知匹配。证据：`src/assets/flower_confirmation_runtime/claude.py:245`。隔离复现中的第二次准备返回“当前回合缺少可核验的完整记录”。
- 两端实际适配器和策略子进程均已复现“内部唤醒后首次 prepare 成功，cancel 后新客户端再次 prepare 失败”。完整证据在 `research/reproduction.md`。
- 用户确认采用“回合来源与确认请求分开保存”的修复方向，同时覆盖两端。
- 实施期间用户补充的 Claude 截图对应真实会话中，技能重复调用写入了 `isMeta=true` 且缺少 origin/turnOrigin 的原生元消息。该消息与真实输入共用 promptId，触发准备失败。证据在 `research/reproduction.md` 的补充记录。

## 需求

- **R1 独立来源**：已核验的当前回合输入来源独立于当前确认请求持久化，支持后续 CLI 进程恢复，来源记录限定为当前回合一份。
- **R2 连续替换**：同一回合内新建、取消、修改材料及连续替换确认都保留有效来源证据。
- **R3 原有许可**：每个新请求独立冻结材料、完整展示、计时、领取和记录执行；来源证据只说明回合来历。
- **R4 生命周期**：人工输入、回合切换、会话重启/退出、原窗口失效和日志漂移继续触发适用的失效或重新核验。
- **R5 来源核验**：原生结构、队列/通知身份、记录边界及人工输入基线继续参与核验。仅提取明确的人工与通知证据，其它附加记录不参与授权判断。
- **R6 分发与回归**：在 Flower 作者源修复两端，验证隔离安装资产与真实 CLI 子进程链路，兼容当前容量和 Windows 工作区改动。
- **R7 兼容**：保留当前请求及 started 执行事实。旧状态在来源充分时精确建立新来源，来源异常时沿原人工流程处理。
- **R8 最小拦截**：按用户在实施后的明确调整，删除与本次授权无关的日志格式、重复来源字段、固定通知外壳/全文、原生 ID 形状及展示/领取固定期限约束。附加记录忽略，必要证据在实际使用处核验。材料一致性、原生归属、人工输入取消、原窗口及单次执行继续有效。

## 范围外

- 软件包发版、外部项目升级和生产操作。
- 默认等待时长、确认界面文案与业务 owner 流程的调整。
- 容量和原生 Windows 既有任务的独立交付。

## 验收

- **AC1（R1/R2/R6）**：两端均覆盖内部唤醒后首次 prepare、cancel 后 prepare、连续 prepare、跨 CLI 进程恢复。
- **AC2（R3）**：替换后的请求完整展示后独立计时，到期可领取并记录 started/completed；旧请求保持单次执行边界。
- **AC3（R4/R5）**：人工插话、迟到/伪造通知、回合或运行变化、日志替换/截断/回滚及窗口退出的对应回归通过。
- **AC4（R6）**：完整本地回归、受影响安装/更新检查通过。匹配变更提交的 Ubuntu/Windows × Python 3.8/3.12 CI 作为后续跨平台交付证据。
- **AC5（R1/R4/R7）**：来源写入与请求替换期间出现人工输入时保留新代次，旧状态兼容、项目更新失效与 started 记账回归通过。
- **AC6（R8）**：新增未知记录、来源单字段/旧字段、通知分块/附加文案、非 UUID 原生 ID、长展示及迟领取均可通过正常自动链路。人工粘贴通知、错请求、材料变化、窗口退出和重复执行仍被拒绝。
