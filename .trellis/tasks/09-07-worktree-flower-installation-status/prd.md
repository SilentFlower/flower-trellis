# 补齐 worktree 的 Flower 安装信息继承

## Goal

通过 worktree skill 创建或准备 linked worktree 时，自动补齐与目标分支相符的 Flower 安装信息，使其可以继续查询和维护 Flower；无法确认版本时给出准确结果。

## Background

- 用户最新明确：重点是相关 .flower 信息应像个人路由偏好一样被带入目标 worktree。仅增加缺失诊断不能解决使用问题。
- 本版替代此前只做诊断、禁止继承安装状态的规划；修订 Brief 已获用户确认，实现、验证和两仓业务推送已完成，任务为 completed。
- 已隔离复现：缺少 lock 和旧 manifest 时，worktree 返回 ready-local，self-check 返回 up_to_date 且项目版本为 null。
- 现有 create 会继承路由偏好，prepare 可显式继承；两者均无 Flower 继承步骤，skill 还明确排除了 state。
- 用户所引另一个项目的具体路径未提供。本任务修复通用能力，在隔离项目验证。

## Requirements

- R1：worktree skill 的创建流程包含 Flower 安装信息继承；已有 worktree 缺失相关信息时也能准备，即使 Trellis 已 ready-local 也不能漏掉。
- R2：补齐缺失的插件声明、锁定版本、安装状态及适用的用户设置。目标持有独立文件，后续更新互不影响。
- R3：目标已有记录优先保留；声明、lock、state 与目标受管内容一致后，才能把来源记录认定为目标安装事实。
- R4：来源与同步范围可见，创建计划包含继承内容；冲突、记录损坏或内容不匹配时报告原因及路径，不覆盖目标版本、不留下部分成功的安装记录。
- R5：只继承必要信息，不共享会话、缓存、事务、备份或控制状态。纯 Trellis 项目继续可用，查询保持只读。
- R6：兜底区分 CLI 最新与项目版本未知；保持原版本来源优先级、真实更新推荐和离线行为，未知本身不触发重装或阻塞式升级提示。
- R7：修改真实源码与配套技能，同步发布快照，保留原有无关变更。

## Acceptance Criteria

- [x] AC1 / R1-R2：来源有效、目标内容相同且 .flower/ 被忽略时，真实 create 后具备独立安装信息，self-check 能读出实际版本。
- [x] AC2 / R1-R2：手动 git worktree add 后，skill 可调用 prepare 补齐记录；重复调用无额外变更，修改目标记录不影响来源。
- [x] AC3 / R3-R4：不同版本、损坏记录、源未提交插件内容或目标摘要漂移时，不覆盖已有文件、不写误导性 state，报告具体原因。
- [x] AC4 / R4：预检无写入，继承载荷变化使创建指纹失效；失败清理本次新增记录，create 原有回滚链继续成立。
- [x] AC5 / R5：缓存、事务、备份、会话及控制状态不复制；跨仓或软链接来源被拒绝；纯 Trellis、偏好继承和迁移不回归。
- [x] AC6 / R6：仍缺版本时不误报项目已最新；同版/异版、旧 manifest、远端新版、离线及提示节流有回归覆盖。
- [x] AC7 / R7：源/快照一致，针对性测试与质量门禁通过，原有 dirty 文件保持原状。

## Non-Goals

- 不自动改目标分支代码或插件内容，不为同步记录执行联网下载、重装或升级。
- 不持续双向同步，不通过软链接或硬链接共享文件。
- 不修改未指定项目的根 Git 忽略策略，不复制旧 manifest 冒充目标安装证据。
- 不纳入原有两个 .flower 配置、GitLab 协作技能及 telemetry-roadmap 变更；不发版、不自动提交或推送。
