# Flower 遥测产品洞察 Roadmap

更新日期：2026-09-06。当前状态：第一批已获完整实施确认，两仓本地实现与验证完成；尚未提交或上线。

## Product Questions

1. 用户实际在哪些平台使用 Flower，主要运行哪些版本？
2. 用户是否持续使用，新增观测实例后续是否回访？
3. 初始化、升级、插件安装在哪里失败，哪些版本质量发生变化？
4. 用户是否采用任务工作流，哪些步骤阻碍任务流转？
5. 哪些核心 Skill 与高级功能被实际使用？

## Batches

| 批次 | 优先级 / 状态 | 产品交付 | 核心数据 | 完成标志 |
| --- | --- | --- | --- | --- |
| 第一批：基础使用洞察 | P0 / 本地完成，待提交上线 | 平台分布、活跃趋势与回访、核心操作质量 | 每日活动、操作终态、版本与运行环境 | 管理端可回答问题 1–3，指标口径与覆盖范围可解释 |
| 第二批：任务流程采用 | P1 / 待规划 | 创建 → 启动 → 完成的采用与流转视图 | 任务随机标识、生命周期节点、发生时间 | 正确处理重复启动、恢复与归档，能够区分未启动与已开始任务 |

| 子阶段 | 交付物 | 依赖 |
| --- | --- | --- |
| 1A：冻结口径 | 平台覆盖表、事件白名单、指标与兼容规则 | 明确首批会话平台范围 |
| 1B：采集与接收 | CLI/hook 采集、独立发送、去重持久化、管理员查询 | 1A；服务端先具备接收新协议的能力 |

| 1D：验证与发布准备 | 隔离跨层验证、旧版本兼容、关闭开关与回退验证 | 1B + 1C；实际部署遵循各仓 SOP |

第一批的功能边界：

- 平台统计以明确运行入口为证据，普通终端调用单独标为 CLI。
- 活跃以安装实例和日期去重，显示的是可观测使用；不显示在线人数或使用时长。
- 核心操作先覆盖初始化、项目升级、自更新与插件安装。
- 数据范围以启用遥测且已接入采集的新客户端为准；旧数据不补造历史使用事件。
- 活跃和回访由同一份日活动数据计算，不建立重复埋点。

## Batch 2

依赖第一批事件接收、安装身份与兼容机制稳定。

- 首先观测任务创建、首次启动和首次完成，定义恢复/重开是否产生新的流转周期。
- 以本地持久化的随机任务标识关联，不上传任务标题、需求或项目路径。
- 将真实任务状态变化作为来源，核实手动 CLI、auto-loop 和 archive 各入口的一致性。
- 检查退回次数和阶段耗时在基础生命周期可信后再扩展。
- 显示“任务流转跨度”；不将其换算为开发工时或开发者绩效。

验收重点：重复执行、恢复和归档不重复计数；无任务 direct edit 不伪造任务。

## Batch 3

依赖第一批的可观测平台清单，并单独验证能力调用入口。

- 候选核心能力：需求规划、实现、质量检查；最终标识以当时的实际 Skill/执行入口为准。
- 区分安装、被触发、进入执行与可证明的结果；模型自行声称调用不能替代执行证据。
- 逐个平台验证显式命令、自动触发和子代理路径，覆盖不完整时显示覆盖范围。
- Plugin、worktree、auto-loop 使用统计按收益逐项加入；业务内容不进入事件。

进入扩大采集的条件：采集来源可复现、重复触发可去重、指标能用于具体产品决策。

## Shared Contracts

- `device_id` 继续表示用户配置目录中的随机安装标识；同一人多配置目录可能对应多个实例。
- 版本、事件类型、错误分类均使用有限白名单或有长度约束的值。
- 遥测关闭与主流程静默契约贯穿所有批次。
- 传输重试不产生新操作，指标不以 HTTP 请求次数计数。
- 管理员分析依赖现有后端鉴权；未接入的平台不能显示为使用量为零。
- 每个新增指标同时交付来源、去重规则、时间口径、分母和已知缺口说明。

## Current Decision

用户于 2026-09-06 确认首批实际会话平台覆盖 Claude Code / Codex，CLI 操作独立统计。第一批跨两个仓库：flower-trellis 负责采集与发送，ai-fund 负责接收、存储、管理员查询和展示。其他平台的实际会话覆盖留到后续适配。
