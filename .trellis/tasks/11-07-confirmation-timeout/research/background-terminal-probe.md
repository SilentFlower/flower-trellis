# 原生后台终端候选与本轮观察

记录日期：2026-11-07。用户提出后台终端可能更适合多数 Harness；这是接入方案候选，未改变已经确定的时长、默认动作和退出取消要求。

## 当前会话的无业务副作用观察

- 使用当前工具 `exec_command` 启动 Python，等待 3 秒后打印一个固定标记；`yield_time_ms=250`。
- 初次调用只返回运行中的 `session_id=64209`，没有标准输出。
- 主会话仍处于本轮活动状态，另等待 5 秒；本轮可见记录没有收到该后台命令的自动完成输出。
- 显式 `write_stdin(session_id=64209, chars="")` 后取得固定标记和 `exit_code=0`，进程已结束。
- 这只证明当前终端接口可后台执行并轮询结果。实验没有结束主回合，也没有关闭主窗口，不能用它证明或否定空闲会话自动续接、原生 Codex TUI 的完成通知或退出取消。
- 没有模型 API 调用、真实线程恢复、业务文件改动、Git 操作或遗留计时进程。

## 两个平台的研究结论

- Claude Code：`research/claude-timeout-capability.md` 第 9 节记录了普通 Bash `run_in_background`、任务完成通知进入模型、正常退出清理以及 resume 不重启旧 Bash 的官方依据。值得优先验证无需新启动器的方案，仍需测试输入竞争、强杀、旧通知和无人输入时实际续接。
- Codex：`research/codex-timeout-capability.md` 第 10 节记录了终端 session、后台 watcher、host 完成事件与实验性清理接口；尚无证据证明后台进程退出会在主回合结束后自动触发新的模型步骤，也不能由 daemon 存活推定用户窗口仍开着。
- [OpenAI Docs：Clean background terminals](https://learn.chatgpt.com/docs/app-server#clean-background-terminals) 提供 list / terminate / clean；这是显式管理接口，不能据此假定窗口关闭会自动清理或到期会自动运行模型。

## 原生后台方案的最小职责划分

1. 主会话登记事项并启动后台等待程序，初始不计时。
2. 短 Stop hook 在完整展示后只负责 arm，不阻塞输入；后台程序再按已定规则等待。
3. 人工输入使旧事项失效；正常退出取消。新启动/手动恢复创建新的运行代号，拒绝旧事项和旧通知。
4. 计时程序只产生到期事件，不运行实现、修复、Git 或新的模型进程。
5. Harness 的原生完成通知负责让仍活跃的主会话处理结果；主会话消费有效决定前再次核验方案、授权、运行代号和人工取消状态。
6. 某个平台没有可靠完成交付或退出取消能力时，不能只运行 `sleep` 后宣称支持，必须回到规划确定补充接入方式。

后台执行载体可共用，完成通知和生命周期仍需按 Harness 验证。本轮未将前台启动器定为必需，也未进入实现。
