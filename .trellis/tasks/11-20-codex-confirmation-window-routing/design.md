# Codex 内置窗口定位与混用后台确认设计

## 边界与契约

共享的 `prepare / wait / claim / result / status / cancel` 与输入序号状态机继续处理授权。Codex 客户端分别核对目标线程、前台进程和队列投递。共享 App Server 的 Unix 控制连接提供磁盘会话元数据及原生队列；内置窗口运行状态以同一会话的原生记录和内核可验证的写锁为依据。

## 内置窗口定位

1. 复用 `thread/read(includeTurns=false)`、精确会话 ID、项目目录、日志首条 `session_meta`、当前回合和输入 Hook。共享服务报告 `notLoaded` 时才进入内置前台识别分支。RPC 错误和不匹配的会话照常报错。
2. 在已解析的同一 `CODEX_HOME` 下关联该 UUID 的 `thread-writer-locks/<thread-id>.lock` 与 `/proc/locks` 的活跃排他持有者。匹配设备和 inode，交叉核对普通文件、同用户 Codex 进程及 PID 出生身份。读取前后复核文件和持有者，防止锁重建或 PID 重用。
3. 通过既有 Unix 控制连接的 `SO_PEERCRED` 确定共享服务进程。内置路径要求写锁持有者是实际前台监听进程，独立于该控制服务。复用 loopback socket 归属和现有 `pidfd` 退出观测。并列候选、锁漂移、权限缺失以及无法区分前台和后台时给出人工诊断。
4. 冻结绑定方式、窗口身份和精确会话锁证据。共享窗口继续按 `codex_tui` 地址绑定。准备、等待、派发、领取和 `started` 依现有调用点复核。绑定退出、会话更换或共享服务取代原运行实例时结束旧许可，新窗口从当前回合重新准备。

## 混用窗口归属

- 共享路径仍枚举已加载会话的原生 TUI 地址，并检查关联进程。额外前台仅在内核证据确认其活跃写锁属于同一用户目录下另一个会话，且当前连接归属证明它没有接入本机共享服务时排除。已绑定目标的内置路径也复核目标会话的写锁和其他可能关联前台。
- 以 `/proc` 文件描述符 inode、控制服务 `SO_PEERCRED` 和可验证的 Unix socket 对端数据建立本机连接证据。优先验证 `NETLINK_SOCK_DIAG` 的 `UNIX_DIAG_PEER` 读接口，由 Python 标准库读取；探针工具 `ss` 只用于本地证据对照。遇到不完整的 socket 快照、未知传输、未归属窗口或同会话歧义，继续采用现有拒绝路径。
- 写锁证明持久会话有唯一写入者。两个共享前台可连接同一个写入者，因此还需保留额外前台检测。额外进程持有其他会话写锁时，也需独立核对它是否同时连接了共享服务。只读检查按当前窗口及确需判定的额外候选进行，避免把状态文件存在或进程名当作放行依据。

## 投递、撤回与兼容

- 沿现有共享控制连接提交 `thread/queue/add`，继续使用 Flower 请求 UUID 作为 `clientUserMessageId`。内置端由 Codex 原生跨进程队列观察唤醒；仍从实际会话记录验证 `client_id` 和唤醒回合。调度程序保持被动读取，目标已经加载在内置服务中。
- 复用 `queueId` 与 `thread/queue/delete`。退出和人工输入先使请求失效，随后撤回精确队列项。投递回执未知沿用现有状态；已经送达时通过领取和 `started` 阻止旧动作。内置端观察队列有原生轮询延迟，实际投递及撤回窗口需要隔离验证。
- 保留有效共享窗口绑定的读写路径；新绑定形态明确标识，既有 pending 请求只在其原契约和窗口证据有效时使用。若有效许可解释发生变化，沿用版本迁移与资产升级取消机制。始终保留旧 `started` 回执的终态记录能力。
- Linux/WSL 功能探测按实际内核与宿主返回判断。Windows 和 Claude 继续使用原适配器；Python 3.8 基线继续可加载。

## 实施风险

- 锁持有者和 Unix socket 对端须一起证明归属。前台正在挂接、连接变化、PID 复用与关闭后重开必须各有反例。
- `0.170.0` 和 `0.171.0` 的队列观察实现已核对。真实跨进程唤醒已在 `0.171.0` 通过；混合版本、精确撤回以及完整确认路径须通过原生验收后才算支持。
- 运行时以 `src/assets/` 为作者源。涉及确认协议时经 Skill-Garden 作者源、发布快照、编译门禁和 Plugin 投影同步 dogfood。回退按同一分发链恢复版本与受管文件，保留用户会话和已开始动作的结果记录。
