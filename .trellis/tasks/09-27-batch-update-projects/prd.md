# 批量更新多个 Flower 项目

## Goal

一次命令更新分布在集中目录和零散路径中的多个 Flower 项目，避免对每个项目重复执行全局升级和项目更新。

## Background

- 当前 `self-update` 每次只接受一个 `--target`，会先检查或升级全局 Flower CLI，再更新该目标项目；现有单项目入口须保持兼容。
- 用户的项目既有集中在父目录下的，也有分散在其他路径的；已认可目录扫描与显式路径合并输入的方案。

## Requirements

- R1：新增 `update-all` 命令，支持重复传入 `--root <dir>` 扫描 Flower 项目，以及重复传入 `--target <dir>` 指定项目；两类输入可组合，重复项目只处理一次。
- R2：`--dry-run` 列出将处理的项目及其预检结果，不安装 CLI，也不修改项目；真实执行需要 `--yes`。
- R3：真实执行时最多升级一次全局 Flower CLI，再逐项目更新到该 CLI 携带的版本；单个项目失败后继续处理其他项目，并在末尾汇总成功、已是最新版、跳过和失败结果。
- R4：脏工作区或存在活动任务的项目默认跳过并说明原因；无效目标和其他预检失败也应指出具体项目和原因；未全部完成时命令返回非零。
- R5：命令只更新 Flower/Trellis 管理内容，不自动修改各项目应用版本，不自动提交或推送 Git。
- R6：无法确认远端最新版本时如实说明，只将落后项目追平到当前已安装的 Flower/Trellis 版本。

## Acceptance Criteria

- [ ] AC1（R1）：同时传入多个 `--root` 和 `--target` 时，发现集中与零散项目，并对重复路径只输出一条项目结果。
- [ ] AC2（R2）：预览展示项目清单、状态和原因，且 CLI 安装、项目文件和更新缓存均不发生写入；未给 `--yes` 的真实执行被拒绝。
- [ ] AC3（R3）：多个待更新项目只触发一次全局 CLI 升级；某个项目更新失败时，后续项目仍会执行，最终汇总每个项目的状态。
- [ ] AC4（R4）：脏工作区、活动任务和无效目标分别显示跳过或失败原因，安全项目仍能继续更新；同一原本干净的 Git 仓库内多个项目不会因本批次前一项的写入被误跳过。
- [ ] AC5（R5）：命令结束后不产生 Git 提交或推送，也不改动项目应用版本文件。
- [ ] AC6（R6）：远端版本查询失败时，汇总明确标注远端未确认，且已知落后于本机 CLI 的安全项目仍可更新。

## Out of Scope

- 自动管理全局项目注册表或扫描用户整个文件系统。
- 跨项目原子回滚；每个项目独立报告结果。
