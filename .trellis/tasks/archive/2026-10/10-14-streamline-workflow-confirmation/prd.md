# 减少检查后停顿并明确中途方案变更确认

## Goal

减少任务执行中的无效停顿，让检查通过后的收尾连续完成，同时保留开工前的改动认知和人工修复决策。

## Background

- 用户确认去掉检查通过后要求再次回复“继续”的步骤。
- 用户明确要求检查发现的问题仍交给人判断，不采用“确定性问题默认自动修复”的新规则。
- 用户希望开工前知道会改什么，但担心中途每次调整方案都重新确认整份 Brief。
- 当前普通检查通过后的停止规则见 `vendor/skill-garden/.trellis/0.6/.agents/skills/trellis-check-all/references/reporting-and-disposition.md:225`；该行为是本次明确要改变的既有约定。
- 实现与恢复阶段不例行重新确认 Brief 的现有约定见 `vendor/skill-garden/.trellis/0.6/.agents/skills/trellis-task-brief/SKILL.md:27`；Brainstorm 的方案变更表述仍在 `overrides/patches/skills/trellis-brainstorm/planning-handoff/readiness-content.md:2` 要求重复评审，需要区分文档刷新和新增待决事项。

## Requirements

- R1：普通交互 Check-All 严格通过，或剩余问题均已由用户有效接受且结论为已接受风险通过，并且不存在阻塞、提交前必需验证缺口或其它未接受实质风险时，同轮完成规范评估，并在其结果可继续时展示提交方案；不要求用户额外回复“继续”。无可交付变更时说明无须提交，不制造空提交。
- R2：用户明确要求“只检查”“检查后停止”时，报告结果后停止，不自动进入后续收尾。
- R3：发现代码问题后统一报告，由用户选择修复范围或接受风险；修复范围确认后连续修复和重检，不对每个问题重复确认。
- R4：首次开工前保留完整 Brief 展示和人工确认，使用户清楚改动行为、影响范围、关键取舍及验收方式。
- R5：规划仍在收敛时持续同步方案；不因每次讨论或文档刷新都进行一次完整 Brief 审批。
- R6：实现细节调整且已确认目标、范围与验收不变时，说明调整并继续，不重新确认 Brief。
- R7：用户明确要求“把 A 改成 B”等调整，已清楚覆盖当前改动及其影响且没有新增待决事项时，同步文档并按指令执行，不再次要求确认同一调整。
- R8：助手提出新增目标、改变验收或扩大影响范围等未获明确决定的变化时，说明相对已确认方案的增量、影响及待决事项，仅请用户决定变化部分；不重复审批无关内容。
- R9：提交方案展示不执行 Git 写入；精确文件范围及提交/推送动作继续等待用户确认。风险接受不由助手推断。
- R10：交互模式和自动任务循环保持各自的执行边界；自动循环已有的授权、结果回录与推进顺序不受本次简化影响。

## Acceptance Criteria

- [ ] AC1（R1、R9）：严格通过及有效风险接受后的通过均同轮进入规范评估；规范为无需变更或已更新时，同轮展示提交方案，未发生自动暂存、提交或推送。无可交付变更时正常结束。
- [ ] AC2（R1、R3）：存在未处置问题、阻塞、提交前验证缺口或规范待决事项时，说明需要的人工决定或验证，并停止在对应环节。
- [ ] AC3（R2、R3、R10）：明确“只检查”或“检查后停止”的指令优先于默认自动推进；没有新增问题自动修复授权，auto-loop 继续服从原运行边界。
- [ ] AC4（R4）：首次开工前仍完整展示 Brief 并等待确认；普通实现意图不能代替首次 Brief 评审。
- [ ] AC5（R5、R6、R7）：规划讨论、实现细节调整和用户已明确授权的 A→B 调整，不触发对相同内容的重复 Brief 确认。
- [ ] AC6（R8、R9）：未授权的范围、验收或风险变化仅展示增量及具体待决事项；存在尚未解决的决定时不执行对应改动。
- [ ] AC7（R6、R7、R8）：新会话和压缩恢复保持同样的确认边界，不因恢复本身再次审批已经确认的方案。
- [ ] AC8（R1—R10）：发布快照、最终生成目标和当前项目实际运行规则一致，相关回归验证通过。

## Non-Goals

- 不增加检查发现代码问题后的默认自动修复，不扩大现有文档事实漂移例外。
- 不取消首次开工 Brief 评审、人工风险接受或精确 Git 计划确认。
- 不调整升级提醒策略、执行模式默认值、发布流程或生产/外部操作授权。
- 不为本次规则变更新建通用审批状态机或替换已有任务运行时。
